# partitioning vs sharding

## 필요 상황

- DB가 단일 테이블, 단일 구조로 한계에 도달한 경우

1. I/O 병목 심화 : 데이터 증가로 인덱스 깊이 증가 -> 디스크 접근 비용 상승
2. 동시성 충돌 증가 : 트랜잭션 경합 및 락 대기 시간 증가
3. 운영 비용 폭증 : 백업, 복구, 배포 시간이 기하급수적으로 증가
4. 물리적 한계 도달 : CPU, 메모리, 디스크 확장의 한계

### 파티셔닝 (Partitioning)


### 샤딩 (Sharding)

- 데이터를 서로 다른 물리적 서버(인스턴스)들에 분산 저장
- Scale Out

## 둘의 차이

1. 물리적 위치가 다르다.
   - 파티셔닝 : 같은 DB의 인스턴스 내
   - 샤딩 : 서로 다른 DB 인스턴스
2. 확장의 방향이 다르다.
   - 파티셔닝 : 단일 서버 내의 최적화 Scale-Up
   - 샤딩 : 여러서버로의 확장 Scale-Out
3. 책임 주체가 다르다.
   - 파티셔닝 : DB 엔진
   - 샤딩 : 애플리케이션 or 미들웨어

### 파티셔닝이 필요한 상황

1. 로그 테이블 : 시간 기준으로 지속적으로 누적되는 대용량 테이블 분리
2. 날짜 기반 데이터 : 최신 데이터 조회 성능이 중요할 때 (조회 조건에 날짜 컬럼이 자주 사용될 때)
3. 대량 데이터 정리 효율 : 오래된 데이터를 통째로 정리하고 싶을 때

### 샤딩이 필요한 상황

1. 대규모 트래픽/데이터 규모가 단일 DB 한계를 넘길 때
2. 글로벌 서비스로 각 지역별 데이터를 물리 분산하여 로컬리티를 확보할 때
3. 단일 서버 사양을 아무리 높여도 성능이 안나올 때 (Scale-Out)
